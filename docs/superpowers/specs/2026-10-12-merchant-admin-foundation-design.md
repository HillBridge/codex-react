# 中大型商户后台前端基座：设计说明

日期：2026-10-12  
状态：待用户审阅

## 1. 目标与已知条件

目标是建立一个可运行、可测试、便于持续扩展的 React 商户后台前端基座，而不是交付只展示页面的样板，也不是在没有后端的情况下宣称产品已经可以上线。

已确认条件：

- 面向中大型商户后台；第一阶段没有现成后端 API、登录系统或 SSO。
- 第一阶段采用单应用 SPA。登录后业务控制台不以 SEO 或 SSR 为主要目标。
- 初始不引入 Express BFF、微前端或多应用工作区。后续按确切需求演进。
- UI 需要深度定制，因此采用无样式组件基础层，不以 Ant Design 作为业务代码的直接基础。
- 多商户的安全隔离属于后端责任；前端负责商户上下文、缓存和界面状态不串显。

成功标准：开发者能启动项目并完成一条订单业务流程；模拟 API 与真实 API 使用同一前端调用边界；工程检查能阻止常见的模块越界；测试证明商户切换和异常处理的关键行为。

## 2. 方案与技术决策

| 关注点 | 第一阶段决策 | 理由与边界 |
| --- | --- | --- |
| 应用形态 | React + TypeScript + Vite 的 SPA | 登录后的高交互管理端优先；静态前端部署简单。SSR 不是 BFF 的前提。 |
| 路由 | React Router | 路由按页面组织；筛选、分页等可分享状态进入 URL。 |
| 服务端数据 | TanStack Query | 请求状态、缓存、失效与刷新统一处理；不能替代后端授权。 |
| UI 行为基础 | React Aria Components | 使用其无样式的表单、选择器、弹层、日期、表格等交互基础，在项目内建立视觉层。 |
| 样式 | CSS 变量设计令牌 + CSS Modules | 控制视觉规范和局部样式，避免业务代码直接绑定底层组件的 DOM 结构。 |
| API 模拟 | MSW，仅开发和测试环境启用 | 保持浏览器与测试使用同一 HTTP 契约；生产构建不启用模拟登录或模拟 API。 |
| 数据表 | 第一阶段使用 React Aria Table 封装订单表 | 当前仅需要服务端筛选、分页及详情入口。出现复杂列管理等需求时再评估 TanStack Table，避免同时维护两套表格抽象。 |
| 包管理 | pnpm，提交锁文件 | 保证本地与 CI 安装结果可复现。 |

Express BFF 的引入条件包括：需要服务端保管登录令牌、实现同源 Cookie 会话、跨后端聚合或对浏览器隐藏内部服务。简单单接口转发不构成引入理由；若只需同源路径，可优先使用现有反向代理或网关。若未来加入 BFF，业务服务仍必须自行校验商户成员关系和资源授权。

## 3. 交付范围与业务切片

第一阶段交付以下可操作流程：

1. 在开发环境使用显著标记的模拟登录进入后台。
2. 显示当前用户可选择的两个模拟商户，并切换商户。
3. 查看订单列表，使用 URL 驱动的筛选和分页。
4. 查看订单详情。
5. 对允许的订单执行一次状态变更，成功后刷新相关列表和详情；冲突时显示错误并重新取数。

示例角色至少包含可读订单与可改订单两类权限，以验证界面权限行为。前端隐藏按钮或路由只改善体验，不构成授权。商品、客户、财务等模块不在第一阶段创建空页面；新增模块应依照订单模块的边界和检查规则扩展。

## 4. 代码结构与依赖边界

```text
src/
  app/                  应用入口、路由、全局 Provider、布局
  pages/                路由页面，组合业务模块
  features/
    session/            会话读取与开发环境模拟登录
    merchant/           商户列表、选择和切换
    orders/             订单查询、详情、状态变更
  shared/
    api/                HTTP 客户端、错误模型
    ui/                 项目级组件封装和设计令牌
    lib/                与业务无关的工具
  mocks/                MSW handlers 与测试数据
```

依赖方向：`app` 和 `pages` 可以组合 `features`；`features` 可以依赖 `shared`，不能深入导入其他 feature 的内部文件；`shared` 不依赖业务模块。每个 feature 通过公开入口暴露页面所需的组件、查询和类型。静态检查约束跨模块深层导入；评审检查新模块是否遵循同一边界。

状态归属：

- 服务端返回的会话、商户和订单数据由 TanStack Query 管理。
- 当前商户以路由中的商户标识为页面上下文；后端必须把它当作选择参数而非授权证明。
- 列表筛选、页码写入 URL。表单输入、弹窗开关与选中项保留在局部组件状态。
- 商户专属查询键必须包含商户标识及所有影响结果的筛选参数。商户切换或登出时取消不再需要的请求，并清理商户专属临时界面状态和敏感缓存。迟到的旧响应不得渲染到新商户页面。
- 不持久化服务端数据缓存或长期凭据到浏览器存储。

## 5. API 契约与可替换边界

初始契约由前端需求定义，并由 MSW 实现；真实后端接入时以契约协商结果调整 `features/*/api` 适配层，页面不直接使用 `fetch`。首批接口：

| 接口 | 用途 | 关键输入/输出 |
| --- | --- | --- |
| `GET /api/session` | 读取当前会话 | 用户身份；未登录返回 401。商户内权限由商户接口提供。 |
| `GET /api/merchants` | 读取可访问商户 | 商户 ID、名称、当前用户在商户内的权限 |
| `GET /api/merchants/:merchantId/orders` | 订单列表 | 状态筛选、搜索词、页码、页大小；返回数据及总数 |
| `GET /api/merchants/:merchantId/orders/:orderId` | 订单详情 | 订单详情及版本号 |
| `PATCH /api/merchants/:merchantId/orders/:orderId/status` | 状态变更 | 目标状态与预期版本号；版本冲突返回 409 |

模拟登录仅存在于开发/测试入口，不能被当作未来生产登录协议。真实接入时由后端/身份系统确定登录流程、Cookie/令牌方案及 CSRF 防护。所有商户范围接口都必须在服务端验证用户商户成员关系、操作权限和资源归属；即使客户端传入另一个商户 ID，后端也必须拒绝未授权访问。

统一请求层将 HTTP、网络失败和可追踪请求 ID 映射成明确错误类型。数据传输对象在 feature 的 API 层转换为业务模型，避免响应格式渗透到页面。列表和详情的 Query key 含商户 ID；状态变更成功后失效相关查询。

## 6. 异常、权限与安全边界

页面至少覆盖加载、空、失败、无权限四种状态。401 清理会话视图并进入登录流程；403 显示无权限；404 显示资源不存在；409 显示状态已变化并刷新订单；429/5xx 提供适度重试入口。读取请求可配置有限重试；非幂等状态变更不自动重试。提交中禁用重复操作，操作成功后显示明确反馈。

前端角色、菜单和按钮规则只控制展示。真正的商户隔离、权限校验、数据查询范围、对象存储和服务端缓存隔离由未来后端实现并测试。上线前必须完成这些后端能力，不能用模拟 API 或前端守卫替代。

## 7. 验证与质量门槛

- 类型检查、格式/静态检查、单元/组件测试、生产构建进入统一脚本与 CI。
- 静态规则阻止 feature 间内部文件互相引用，并约束页面绕过 feature API 直接请求接口。
- 测试覆盖商户 ID 与筛选参数形成独立查询键、商户切换不显示旧订单、迟到响应不串显、权限展示、401/403/409/5xx 的主要反馈及订单变更后的数据刷新。
- 端到端测试覆盖模拟登录、商户切换、订单筛选/分页、详情和状态变更。
- 代码评审清单检查商户上下文、服务端授权前提、加载/空/失败态、查询失效、可访问性及新增测试。

第一阶段的验收命令应能在没有真实后端的环境中运行。生产构建不得启动 MSW；由于真实后端和身份系统尚不存在，生产构建通过不等于可上线。

## 8. 实施顺序与明确不做的事

实施分为：工程初始化与质量门槛；项目 UI 基础与布局；会话/商户上下文；订单纵向业务切片；测试与文档。每阶段保留可运行状态，并在最终计划中细化为文件和验证命令。

第一阶段不做真实身份认证、后端授权、数据持久化、BFF、SSR、微前端、多应用工作区、全量业务模块或自建通用低代码框架。后续是否引入这些能力，必须由明确的业务或部署需求驱动。
